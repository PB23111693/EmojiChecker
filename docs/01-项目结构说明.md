# 项目目录结构说明

编制日期：2026 年 10 月 29 日
适用范围：仓库 `SE-EmojiChecker`，对应设计方案 5.4 的工程结构约定

## 1 组织原则

三条约束决定当前结构。

第一条，指导书要求“C/S 与 B/S 混合架构、修改版 MVC、分层后端”，目录必须让评审在三十秒内看出客户端、Web 前端、后端、AI 与数据库的边界。

第二条，最终提交包要求源码、文档、报告、视频、贡献表五类材料齐备，因此仓库内 `docs` 保存随代码演进的设计文档，仓库外 `交付材料` 保存归档成品。

第三条，多人并行开发需要最小化文件冲突，按“角色页面 + 后端分层 + 独立 AI 进程”切分目录，每个人主要修改自己那一层。

## 3 分层职责与约束

| 层 | 允许做的事 | 禁止做的事 |
| --- | --- | --- |
| controller | 解析请求、绑定参数、调用 service、组装统一响应 | 写业务判断、直接拼 SQL |
| service | 权限、状态、幂等、时间窗、统计口径、事务提交 | 依赖 FastAPI 的 Request 或 Response |
| repository | 构造 SQLAlchemy 查询、返回实体 | 判断角色、抛业务异常以外的逻辑 |
| model | 字段、约束、索引、关系 | 业务计算、跨表查询 |
| schema | 类型校验、格式约束 | 查库、访问配置以外的外部状态 |

三条硬约束：

1. 所有角色与数据归属判断必须落在 service，前端隐藏菜单只是导航行为。
2. 所有时间在库内以 UTC 保存，读出不带时区时补 UTC，输出为带时区的 ISO 8601。
3. 列表、统计、导出必须复用 `EmojiRepository` 的同一套筛选条件，禁止各写一遍。

前端约束：

- `views` 只保留模板与图表配置，筛选、提交、轮询等逻辑放入 `controllers` 或 `composables`。
- `api` 模块是唯一网络访问入口，统一处理 `{code, message, data}` 与 401。
- 路由守卫按角色放行，服务端仍执行最终校验。
